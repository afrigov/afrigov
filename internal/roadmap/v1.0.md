# v1.0 — What "stable" has to mean

1.0 is a promise: class names, token names and the pack schema will not break without a major version. We can only make that promise once we have evidence the current shapes survive contact with real services, real assistive technology, and languages that write right to left. The list below is the evidence, in the order it should be gathered.

## 1. Finish the surface (0.2)

The 0.2 inputs are the last things likely to change the pack schema, so they go first.

- Phone number, national ID, region selector, currency display, character count, service card, details, language switcher.
- Pack schema v1: `tokens/packs/pack.schema.json`, validated in tests. Fields: strings, language, currency (code, symbol, position, locale, hint), id (name, short, document, hint, length, authority), regions, examples, flag, flagDirection, optional `flagSvg`.
- SVG flag support for flags that are not bands (South Africa, Kenya's shield, Ghana's star), with bands as the fallback.

## 2. Right-to-left

Arabic is an official language in a third of the continent. The CSS still uses physical properties in places (`border-left`, `padding-left`, `margin-left`, `text-align: right`). Before 1.0:

- Convert to logical properties (`border-inline-start`, `padding-inline-start`, `margin-inline-start`, `text-align: end`).
- Add an RTL run to the axe suite (`dir="rtl"` on the docs page).
- Ship one Arabic-default pack (Morocco or Egypt) to prove it. Morocco is the better first: Arabic and French both official, so it tests the language switcher too.

## 3. A complete service journey

Components are not enough; agencies copy pages. Add page templates to the docs, each a full HTML file:

- Start page, question page, check-your-answers page, confirmation page, error page, service home with cards.
- Each template passes axe and the touch-target test as a page, not just as components.

## 4. Evidence from real use

- **One real service built on it**, end to end, by someone other than us. A ministry, a state, a civic-tech group, or a faithful rebuild of a real form (NIN enrolment, eCitizen passport renewal) if no partner is ready. Record what broke.
- **Manual assistive technology pass** on every component, logged in `internal/at-testing.md`: NVDA with Firefox, VoiceOver with Safari on iOS, TalkBack with Chrome on Android. axe catches about a third of real problems; the rest need a person.
- **Low-end device pass**: an Android Go phone on a throttled 2G profile, and Opera Mini extreme mode, with screenshots in the docs.
- **Browser support table verified**, not assumed.

## 5. Packs

At least six, covering the continent's main language and script situations:

| Covers                       | Pack                                           |
| ---------------------------- | ---------------------------------------------- |
| Anglophone                   | Nigeria, Kenya, Ghana (shipped)                |
| Francophone, suffix currency | Senegal (shipped)                              |
| Arabic, RTL, bilingual       | Morocco                                        |
| Multilingual, complex flag   | South Africa                                   |
| Lusophone                    | Mozambique or Angola, if a contributor appears |

Every pack with non-English strings has a native-speaker review recorded in an issue before 1.0.

## 6. Documentation

- A page per component: when to use, when not to, the HTML, the accessibility notes, the pack fields it reads.
- A page per pack.
- A versioning and deprecation policy page.
- An accessibility statement for the docs site itself.

## 7. Governance

- `CODEOWNERS`, a release cadence (monthly minors until 1.0), and at least two outside contributors merged. Translations count.
- Semantic versioning enforced by a changelog check in CI.

## Sequencing against the version roadmap

The README roadmap is version-ordered: 0.3 is the audit CLI and scoreboard, 0.4 is right-to-left with Morocco plus the page templates, then 1.0. The audit does not change the API, so it is not a 1.0 blocker, but it is built first because 1.0 needs real adoption and the audit is how adoption happens.

## Explicitly not required for 1.0

- The audit CLI and scoreboard (0.3). Valuable for adoption, irrelevant to API stability, and built before the 1.0 blockers for that reason.
- The Figma library (0.4).
- Framework wrappers.

## Honest estimate

Working part-time alongside paylocal and ussdkit: 0.2 is about six weeks, RTL and logical properties one to two, templates two, the AT and device passes two, documentation three. Call it four months of steady work if a partner service turns up along the way, longer if we have to build the reference service ourselves. The pack reviews depend entirely on contributors, which is why the issues are open now.

Target: **1.0 in Q1 2027**, and we do not cut it early to hit the date.
